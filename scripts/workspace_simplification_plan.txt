WORKSPACE MANAGER PERMISSION SIMPLIFICATION PLAN
Generated: 2026-07-21
==============================================================

GOAL
----
In the Workspace Manager, every child item (module, menu, button,
widget) should have only 3 possible states controlled by role:

  ACTIVE  = fully enabled and visible (IsVisible=1, IsEnabled=1)
  VIEW    = visible but disabled    (IsVisible=1, IsEnabled=0)
  DISABLE = hidden                  (IsVisible=0, IsEnabled=0)

No more matrix of 58+ permission checkboxes per role per child.
No more auto-granting all module permissions to workspace roles.

==============================================================
CURRENT BEHAVIOR (PROBLEM)
==============================================================

When you assign modules/roles to a workspace and save, the system
auto-grants ALL module permissions to ALL workspace roles:

  INSERT INTO dbo.RolePermissions
  SELECT wr.RoleId, p.PermissionId, 1, GETDATE()
  FROM dbo.WorkspaceRoles wr
  CROSS JOIN dbo.WorkspaceModules wm
  INNER JOIN dbo.Permissions p ON p.ModuleId = wm.ModuleId

This creates hundreds of RolePermission rows and bloats the
permission resolver to 58+ keys per workspace user.

==============================================================
NEW BEHAVIOR (SIMPLIFIED)
==============================================================

1. GLOBAL ROUTE PERMISSIONS (UNCHANGED)
   --------------------------------------
   The ~58 permissions used in requirePermission() middleware
   remain active. These protect API routes globally.

   Users get these permissions through their ASSIGNMENT
   compatibility role (e.g., Teacher -> Teacher role -> library
   permissions). This is handled by getActiveAssignmentPermissions()
   in permissionResolverRepository.js.

2. WORKSPACE PERMISSIONS (REDUCED TO 3)
   --------------------------------------
   Only 3 workspace-level permission keys exist:
   
     workspace.view     - can access the workspace
     workspace.activate - can enable/activate features
     workspace.disable  - can disable/hide features

   These are granted per workspace role (in WorkspaceRoles).

3. WORKSPACE CHILD STATES (EXISTING COLUMNS)
   ------------------------------------------
   Each workspace child table already has IsVisible and IsEnabled:
   
     WorkspaceModules  (IsVisible, IsEnabled)
     WorkspaceMenus    (IsVisible, IsEnabled)
     WorkspaceButtons  (IsVisible, IsEnabled)
     WorkspaceWidgets  (IsVisible, IsEnabled)

   These columns CONTROL what the user sees and can use.
   No additional permission lookup needed.

4. PERMISSION RESOLVER (SIMPLIFIED)
   ----------------------------------
   Remove the workspace module permission auto-grant layer.
   
   Current layers:
     Layer 1: RolePermissions (global, from assignment compatibility)
     Layer 2: UserPermissionOverrides (individual exceptions)
     Layer 3: WorkspaceModulePermissions (auto-granted, TO BE REMOVED)
   
   New layers:
     Layer 1: RolePermissions (global, from assignment compatibility)
     Layer 2: UserPermissionOverrides (individual exceptions)
     Layer 3: Workspace view/activate/disable (workspace access only)

RISKS
==============================================================

   show the 58 active permissions. You may want to hide the
   workspace module permissions from that UI.

3. If any role depends on workspace module permissions instead of
   global RolePermissions, they will lose access.
